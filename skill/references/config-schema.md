# Project Manifest Schema Reference

> Defines the configuration object generated in Phase 2 (CONFIGURE) and consumed by Phase 3 (SCAFFOLD).
> All template variables in generated files are derived from this manifest.

---

## 1. Purpose

The project manifest captures everything the skill needs to know about the target project. It is built interactively during Phase 2, populated with auto-detected defaults from Phase 1. The manifest is held in memory during execution — it is not written to disk unless the user explicitly requests it.

---

## 2. Full Schema

```yaml
# ============================================================
# Project Manifest — generated by /setup-workflow Phase 2
# ============================================================

project:
  name: string              # Required. Display name. Example: "Acme Portal"
  description: string       # Required. One-line purpose.
  domain: string            # Required. Business domain. Example: "e-commerce", "healthcare", "fintech"
  story_id_prefix: string   # Required. 2-5 uppercase chars. Example: "ACME"

topology:
  type: enum                # Required. One of: single-repo | multi-repo | monorepo
  repos:                    # Required. List of repos.
    - name: string          # Repo short name. Example: "backend"
      purpose: string       # What it owns. Example: "Business APIs"
      path: string          # Relative path. Example: "./backend"
      has_code: boolean     # false for memory/context repos
  memory_repo: string|null  # Name of context-only repo. null for single-repo.

stack:
  backend:                  # Omit if no backend
    language: enum          # python | go | java | kotlin | node | csharp | rust
    version: string         # Language version. Example: "3.12"
    framework: string       # Web framework. Example: "fastapi"
    orm: string|null        # ORM. Example: "sqlalchemy"
    test_runner: string     # Example: "pytest"
    linter: string          # Example: "ruff"
    formatter: string       # Example: "ruff format"
    type_checker: string|null # Example: "mypy"
    coverage_tool: string   # Example: "pytest-cov"
    coverage_threshold: number # Default: 80

  frontend:                 # Omit if no frontend
    framework: string       # Example: "react"
    language: enum          # typescript | javascript
    version: string         # Example: "18.3"
    build_tool: string      # Example: "vite"
    test_runner: string     # Example: "vitest"
    linter: string          # Example: "eslint"
    formatter: string       # Example: "prettier"
    component_lib: string|null # Example: "antd"
    state_mgmt: string|null # Example: "redux"
    css_approach: string    # Example: "tailwind"

  database:                 # Omit if no database
    primary: string         # Example: "postgres"
    secondary: string|null  # Example: "mongodb"
    migration_tool: string  # Example: "alembic"

  infra:                    # Optional
    containerized: boolean  # Default: false
    ci: string|null         # Example: "github-actions"
    deploy: string|null     # Example: "docker-compose"

agents:
  roster: list[string]      # Auto-determined, user can override.
                             # Values: scrum-master, architect, ba-analyst, dev-backend,
                             # dev-frontend, dev-rbac, ai-engineer, devops-engineer,
                             # qa-engineer, code-reviewer, linter, qa-e2e

hooks:
  auto_format:
    enabled: boolean        # Default: true
  safety:
    enabled: boolean        # Default: true
    blocked_patterns: list  # Auto-populated from stack
  session_start:
    enabled: boolean        # Default: true

git:
  branch_pattern: string    # Example: "feat/{{PREFIX}}-{NNN}-{kebab}"
  commit_pattern: string    # Example: "<type>(<scope>): <subject>"
  protected_branches: list  # Default: ["main"]
  squash_merge: boolean     # Default: true

humans:
  product_owner: string     # Name of PO
  primary_dev: string|null  # Name of primary dev (if known)
```

## 4. Validation Rules

Before proceeding to Phase 3, validate:

| Field | Rule |
|---|---|
| `project.name` | Required. Non-empty string. |
| `project.story_id_prefix` | Required. 2-5 uppercase alpha characters. No spaces, no numbers. Regex: `^[A-Z]{2,5}$` |
| `topology.type` | Must be one of: `single-repo`, `multi-repo`, `monorepo` |
| `topology.repos` | At least 1 repo. |
| `stack` | At least one of `backend` or `frontend` must be present. |
| `agents.roster` | Must include `scrum-master`, `qa-engineer`, `code-reviewer` at minimum. |
| `git.protected_branches` | At least one branch. |
| `stack.*.coverage_threshold` | Integer, 0-100. |
| `stack.database.migration_tool` | Required if `stack.database` is present. |

### Derived Variables

Some variables are computed, not directly from the manifest:

| Variable | Derivation |
|---|---|
| `{{BACKEND_LINT_CMD}}` | linter name + standard flags (e.g., `ruff check --fix`) |
| `{{FRONTEND_BUILD_CMD}}` | If build_tool = "vite" → "vite build"; if "webpack" → "npm run build" |
| `{{COMMIT_FOOTER}}` | Always `"Refs: {{PREFIX}}-{NNN}"` |
| `{{BLOCKED_PATTERNS}}` | Universal patterns + migration tool patterns + stack patterns (see hook-catalog.md) |
| `{{TOPOLOGY_TABLE}}` | Markdown table generated from `topology.repos` array |
| `{{AGENT_ROSTER_TABLE}}` | Markdown table generated from `agents.roster` with descriptions |

## 6. Agent Roster Selection Logic

The roster is auto-determined based on the manifest, then presented to the user for confirmation:

| Condition | Agents Added |
|---|---|
| Always | `scrum-master`, `code-reviewer`, `qa-engineer` |
| `stack.backend` present | `dev-backend` |
| `stack.frontend` present | `dev-frontend` |
| Auth/RBAC layer detected | `dev-rbac` |
| `topology.type` = multi-repo OR scale = large | `architect` |
| FRD/PRD exists | `ba-analyst` |
| Lint tooling detected in stack | `linter` |
| Both frontend and backend present | `qa-e2e` |
| AI/ML dependencies detected | `ai-engineer` |
| Infrastructure files detected | `devops-engineer` |

### Scale-Based Adjustment

| Scale | Typical Agent Count |
|---|---|
| Small (1 repo, 1 layer, < 10 features) | 4-5 |
| Medium (1-2 repos, 2 layers, 10-30 features) | 6-8 |
| Large (3+ repos, 3+ layers, 30+ features) | 8-12 |
